# План выполнения практической работы: backpressure

> Состояние этапа B: реализованы повторы с устойчивым счётчиком, подтверждённая
> DLQ, обработка shutdown/redelivery, тесты TestRabbitBroker/Testcontainers,
> метрики и оркестраторы экспериментов/защиты. Подготовлены ответы на 12 вопросов.
> Полная повторная матрица E1–E4 и графики сохранены в
> `docs/experiments/2026-10-21-final`. Ранние прогоны со сбоем памяти
> оставлены в архиве и исключены из выводов.
> Текущие результаты и команды — в README и `docs/backpressure-defense.md`.

Ниже сохранён исходный план. Описания начального состояния и будущих шагов
относятся к моменту его составления; фактический результат указан выше и в README.


Порядок работы строго последовательный: сначала ты полностью завершаешь этап A,
передаёшь проверяемый результат, затем второй человек выполняет этап B на его основе.
Второму человеку не нужно начинать свою часть заранее. После передачи он также
самостоятельно исправляет обнаруженные дефекты в общей реализации.

Дедлайн в задании — 22.10, время сдачи не указано. Тесты, измерения и подготовка
демонстрации входят в обязательный объём работы, поэтому после этапа A нужно
оставить время на полноценный этап B.

## Что уже есть в репозитории

- FastAPI, PostgreSQL, Docker Compose, CI, Ruff и pytest.
- MLflow Registry, обучение, alias `champion` и однократная загрузка модели при
  старте API. Alias разрешается в версию при запуске; версия не зашита в коде.
- Inference через `run_in_threadpool`, валидация текста и проверки загрузки модели.
- Сейчас `/process` сразу возвращает предсказание. RabbitMQ, FastStream-воркера,
  пакетного источника и таблицы результатов задач пока нет.

Обучение и MLflow не нужно создавать заново. Основная переделка — перенести
inference из API в отдельный воркер и добавить управление потоком задач.

## Общий контракт реализации

1. Независимые процессы: API, пакетный источник и FastStream-воркер. Источник и
   API передают задания воркеру только через RabbitMQ. Результаты пишет воркер
   в PostgreSQL. API не загружает модель и не вызывает inference.
2. Сообщение содержит как минимум `task_id`, `text`, `created_at`; при повторной
   публикации той же задачи `task_id` сохраняется. Формат сообщений и названия
   exchange, routing key, основной очереди и DLQ фиксируются на этапе A.
3. Рекомендуемый минимальный вариант хранения — таблица готовых результатов с
   уникальным `task_id`. Источники не создают строки `PENDING`: это устраняет
   двойную запись «создать задачу в БД, затем опубликовать» на входе системы.
   Если всё же вводится таблица статусов, отказ публикации обязан убирать `PENDING`.
4. Общий publisher делает одну попытку публикации с publisher confirms и явно
   сообщает об отказе. Пакетный источник повторяет попытку с ожиданием; API при
   переполнении сразу возвращает отказ. Эти две политики нельзя смешивать.
5. Настройки вынесены в конфигурацию: адрес брокера, лимит очереди, конкурентность,
   `prefetch_count`, задержка inference, timeout публикации, Retry-After,
   число попыток обработки и время штатной остановки. Имена и alias модели
   остаются настройками, как сейчас.
6. Для сравнения нужны два режима конфигурации: с ограничениями и без них.
   Удобнее использовать разные очереди или воспроизводимое пересоздание пустого
   стенда, чтобы не конфликтовали аргументы уже объявленной очереди.

Начальные параметры для демонстрации, не результаты эксперимента:

## Точка передачи от тебя второму человеку

Передавать этап A после выполнения всего чек-листа:

- [ ] Есть один зафиксированный commit с A1–A7, команды установки и запуска.
- [ ] Модель доступна в MLflow, alias настроен; обучение не требуется повторять
      для каждого запуска эксперимента.
- [ ] Из чистого состояния запускаются API, брокер, БД, один воркер и источник.
- [ ] Задача доходит до результата в PostgreSQL с правильными ID и версией модели.
- [ ] Повторная доставка того же task_id оставляет один результат.
- [ ] Медленный воркер заполняет очередь; источник замедляется и продолжает
      работу после освобождения места, не пропуская отвергнутую запись.
- [ ] API при заполнении отвечает `503` с обоснованным `Retry-After`, без `PENDING`.
- [ ] Записаны настройки, формат сообщений, схема БД, ack_policy и оставшиеся
      задачи B1–B7. Второму человеку не нужно угадывать интерфейсы.
- [ ] Ruff, форматирование и актуальные тесты этапа A проходят.

Передача означает завершение твоего блока. Вторая часть не должна зависеть от
обещания позднее дописать publisher, воркер, API или схему БД.

## Обязательные эксперименты второго человека

| Режим | Ограничение очереди / prefetch | Воркеры | Что сравнить |
| --- | --- | --- | --- |
| E1 | Без ограничений | 1 | Базовое накопление сообщений и поведение памяти/задержек. |
| E2 | Включены | 1 | Ограничение очереди, адаптацию источника и установившуюся скорость. |
| E3 | Без ограничений | 2 | Как масштабирование влияет на накопление и обработку без защиты. |
| E4 | Включены | 2 | Рост пропускной способности и автоматический рост скорости источника. |

В режиме без ограничений остаётся тот же код inference и размер пула на один
воркер; отключаются соответствующие ограничения очереди и prefetch. Эксперименты
имеют одинаковую длительность, достаточно большой конечный входной файл,
одинаковый размер сообщения, модель и задержку inference. Каждый запуск начинается
из одинакового состояния; отдельно выделяются разгон и установившийся участок.

Снимать показатели регулярно, например раз в секунду, и сохранить:

- `messages_ready`, `messages_unacknowledged` и их сумму;
- потребление памяти каждого компонента и суммарно обоих воркеров;
- принятые брокером задачи/с и завершённые задачи/с;
- полное время задачи от первой попытки публикации до коммита результата,
  отдельно время обработки; p50/p95 по сопоставимым временным интервалам;
- число отказов API и время ответа на них;
- баланс уникальных задач: принятые = результаты + DLQ + ещё находящиеся
  в обработке/очередях, включая retry. После полного завершения очереди пусты.

Лимит длины RabbitMQ относится к `ready`, сообщения `unacked` считаются отдельно.
Для одного consumer на воркер при prefetch C суммарно в работе обычно не больше
W × C сообщений; это нужно учитывать при чтении Management UI и графиков.
Семантику переполнения и повторной постановки проверить на выбранном типе и версии
очереди. См. [Queue Length Limit](https://www.rabbitmq.com/docs/maxlength).

Management API допустим для измерений; решение о замедлении источника должно
приходить из результата публикации, а не из опроса глубины очереди.

## Что обязательно объяснить в README и на защите

- Почему alias разрешается один раз на запуск воркера и как узнать фактическую
  версию модели; почему добавление второго воркера не требует изменения кода.
- Как связаны число обработчиков, пул и prefetch; как health-check подтверждает,
  что event loop не заблокирован.
- Как `reject-publish` вместе с publisher confirms сообщает об отказе; почему
  `drop-head`, фиксированный rate limit и неограниченный буфер не подходят.
  Опрос глубины очереди имеет задержки и гонку между проверкой и публикацией.
- Почему пакетный источник ждёт — это backpressure; почему API отказывает
  внешнему клиенту — это load shedding. На выполнение Retry-After клиентом
  система не рассчитывает.
- Конкретный `ack_policy`, момент коммита и ack, последствия подтверждения до
  результата, счётчик повторов, судьба poison message и DLQ.
- Почему UNIQUE/PRIMARY KEY и атомарная запись защищают от дублей, а схема
  «проверить наличие, затем вставить» без ограничения не защищает.
- Границы гарантий доставки: потеря publisher confirm может привести к повторной
  публикации, поэтому сохраняется task_id. Подтверждение брокера и подтверждение
  обработки воркером решают разные задачи; для сохранности нужны также durable
  очереди и persistent сообщения. См. [Acknowledgements and Publisher Confirms](https://www.rabbitmq.com/docs/confirms).
- Что показали фактические измерения, включая влияние второго воркера.
  Не подменять результаты ожидаемыми значениями и скриншотом одного момента.

Подготовка теории: ты прорабатываешь вопросы 1–6 из задания, второй человек —
7–12 и добавляет краткие ответы в материалы защиты. Перед сдачей оба читают все
ответы: распределение подготовки не означает, что отвечать будет только автор.

В исходном задании есть расхождение: заявлено 10 баллов, но суммы перечисленных
разделов дают 7,5. Отдельные баллы за тесты и исследование не расписаны; сами
требования обязательны и из плана не исключаются.
